# RG-02: 複数Result Setの取得と表示

RG-01のコミット`2b81b54`に依存。既存MySQLプロバイダとタブ所有モデルを再利用する。対象は1回のSQL実行で返る複数結果の分離と保持。RG-03のショートカット追加、CSV規約/Import、他DB対応は含まない。

## 問題と変更後の動作

以前は単一文のみ実行可能で、結果モデルも1つだった。今後はMySQL接続で最大20文のSELECT/INSERT/UPDATE/DELETEをまとめて実行し、それぞれの列・行・影響行数・省略状態・取得完了状態を順序付き`resultSets`で返す。

- 入力を`sqlparser`で解析し、全ての文に既存の読み取り専用/セッション操作禁止チェックを適用する。SQLの単純な文字列分割やASTからのSQL再生成はしない。
- sqlx 0.8.6の`fetch_many`は行と結果終端を返すが、0件の結果では列情報を公開しない。そのためパーサーが消費した文の開始位置と次トークン位置から**原文の範囲**を取得し、各文を`describe`で事前確認する。位置はUnicode文字単位からUTF-8バイト位置へ変換し、リテラル・コメント・CRLFを保つ。
- 実行は原文全体を`raw_sql(...).fetch_many`で**1回だけ**送信する。各文を順次別実行する方式ではない。ドライバの完了通知で結果を区切る。
- 事前確認に失敗した場合はSQLを実行しない。実行段階のエラー/タイムアウトでは取得済み結果を保持して`error`を返す。UIはその応答を成功扱いにせず、失敗バナー・履歴・状態を表示する。
- `columns`/`rows`は先頭結果、`affectedRows`は全結果合計、`truncated`は全結果のいずれか、という既存IPC互換フィールドを残す。旧形式のデモ/テストGateway応答も表示可能。
- 結果タブをエディタタブの下に配置。結果ごとにページ・ページサイズ・縦横スクロールを保持し、エディタを戻しても選択結果が変わらない。0件の列と更新件数を区別する。容量上限で行を保存できなかった結果を「0件」と誤表示しない。
- 再実行では該当実行の結果・表示位置をリセット。実行中に以前の完了メッセージを現実行の成功として表示しない。CSVは選択結果のみ、複数結果の場合はファイル名に結果番号を付ける。更新件数とメッセージ画面ではCSV出力を無効化する。

## 上限・制約

SQLは100KB、最大20文。複数文ではSELECT/INSERT/UPDATE/DELETEのみ。DDL/EXPLAINは1文ずつ、CALL/トランザクション制御/セッション変更は引き続き未対応。空の文（先頭や連続した区切り）は受け付けない。末尾の区切りは許可。デモは従来どおり単一のサンプルSELECTのみ。

各結果の保持は1,000行、各値5,000文字/バイナリ2,500バイト。列名・セル文字列・セル管理領域を合わせた保持予算は実行全体で5,000,000バイト。結果ごとに予算をリセットしない。1行が残予算を超えた場合はその行以降を保存せず、後続結果を得るために読み捨てる。上限での行/値の省略と、取得途中の失敗を別々に表示する。

この予算はプロセス全体のメモリ上限ではない。ドライバは少なくとも1行分のパケットを保持し、互換フィールドの先頭結果コピー、IPC変換、Reactの保持、既存履歴（50件）には別のメモリが必要。全件をメモリに集める処理は追加していない。

事前確認から取得まで15秒の待機上限（プール取得最大8秒は別）。省略後も通信/サーバー処理は継続するため、全件の取得負荷を抑えるにはSQL自体にLIMITが必要。全体トランザクションはなく、途中エラー・タイムアウト・中断で更新を巻き戻す保証はない。明示的な中断はRG-01の方式を維持し、その実行の途中結果を破棄して接続を解放する。

事前確認は各文が実行前のスキーマで解釈できる必要がある。スキーマを変えるDDLを複数文に混在させない。同時に外部からスキーマ変更される場合の整合性や全てのSQL方言は保証しない。
